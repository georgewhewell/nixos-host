# SG2002 stability lab report — 2026-08-30

This report covers the original LicheeRV-Nano-W attempt on `strix-1`, the
camera-board handoff on `strix-4`, and the explicitly authorised PicoClaw
fallback on `fuckup`.  Production `nanokvm` (`192.168.23.17`), production
camera `licheerv` (`192.168.23.29`), and their runners were not touched.
The camera-board host later flapped and the PicoClaw fallback had no usable
RJ45 carrier.  After the requested physical restoration, five consecutive
corrected camera software cycles completed over RJ45/NFS with no old-root
leak, failed unit, swap, or relevant kernel error.  A later camera queue
budget A/B also succeeded.  A later receiver recovery A/B completed 62/62
rapid restarts plus a continuous three-frame capture while hiding malformed
startup frames from userspace.

## Baseline and transport result

The isolated worktree is `/mnt/Home/src/nixos-nanokvm-sg2002-stability`,
branch `agent/sg2002-stability`, based on master `8ebab1f`; camera commit
`a1f0ea8` was cherry-picked as `53808d3`.  The existing runner was invoked
on `strix-1` with:

```text
sudo -n env NANOKVM_ATTACH=none NANOKVM_STATUS_LISTEN=0 <runner>/bin/usb-boot \
  --rom-dl-verbose --rom-dl-timeout 900 --attempts 10 --wait 120
```

The board reproducibly entered CVITEK BootROM (`3346:1000`), U-Boot
fastboot (`18d1:d00d`), and the Linux composite gadget (`1d6b:0104`).  The
baseline `licheerv.mainline.live.eth-nfs` image then exposed no `eth0` and
never reached its RJ45 DHCP/NFS/SSH handoff.  Its generated *requested*
module lists contained `libcomposite`, `usb_f_acm`, `configfs`, and
`usb_f_ecm`, but no GMAC names.  The current SG2002 mainline config compiles
`STMMAC_ETH`, `STMMAC_PLATFORM`, and `DWMAC_SOPHGO` as built-ins
(`pkgs/sg2002/linux-mainline/config.nix:454-458`), and its module-closure log
classifies those roots as `builtin`; therefore the missing list entries are
not proven to be the cause of this run's absent `eth0`.  Kernel probe errors
were not captured before the board wedged, so Ethernet bring-up remains an
open hardware test.

Commit `ba06f85` keeps the three GMAC roots explicit in the catalog entry in
`lib/catalog.nix:404-420` (future-proofing if Kconfig changes) and removes the
unbounded `ttyGS0` status writer.  That writer could block in `gs_close()`
when the host did not drain ACM; after the baseline runner was interrupted,
the board stopped enumerating.

### Camera reserved-pool queue budget

The first post-stability camera load attempt failed `VIDIOC_STREAMON` with
`ENOMEM` even though global `CmaFree` remained about 24 MiB.  The CSI node
uses its own 32 MiB reserved-memory allocator: each 5,529,600-byte RAW frame
is rounded to an 8 MiB allocation, and an additional 8 MiB scratch frame is
required at stream start.  A multi-buffer MMAP request could therefore
consume the private pool with no allocation headroom; global CMA could not
satisfy that private allocation.

Commit `c97560a` adds patch 0062, limiting the total CSI queue to two capture
buffers (including buffers added through `CREATE_BUFS`).  On the old kernel,
the same helper failed at STREAMON with `Cannot allocate memory`; on the new
kernel boot `cc886756-cea2-4248-a798-38af83eeced3` it captured a
5,529,600-byte frame successfully while swap stayed zero and memory returned
after teardown.  NFS and SSH remained on the board's RJ45; the USB gadget was
only the bootstrap/fallback management path.

Rapid repeated STREAMOFF/STREAMON then exposed a separate GC4653 lifecycle
fault: the queue-capped kernel completed 9/12 default-control starts in a
corrected baseline and logged six new CSI CRC/ECC events.  Vendor source uses
the three-register `gc4653_standby()`/`gc4653_restart()` sequences without
asserting reset or disabling MCLK between them, whereas patch 0053 performed
the standby writes and immediately hard-reset the sensor.

The retained-power/vendor-restart hypothesis failed decisively after strix-4
returned.  Kernel boot `66f52abd-88a7-4ae7-aa30-db870ed79186` captured its
first frame but timed out on starts two and three, despite the sensor registers
reading `0100=09`, `0317=00`, and `031c=c6`.  Rebinding only the capture/CSI
platform driver did not recover a frame; rebinding only GC4653, which performs
the hard sensor power cycle, immediately restored a complete 5,529,600-byte
frame.  The receiver therefore was not proven stale, while the sensor's
retained-power MIPI state was unusable.

A narrower hard-reset experiment kept the existing power cycle and full mode
reload but delayed power-off after standby.  A 35--40 ms delay improved the
matrix to 10/12 with three logged CSI events on boot
`6dac5fe5-4d9f-4281-91c4-175f3fa3d059`; increasing it to 100--120 ms regressed
to 8/12 with four CRC/word-count failures on boot
`3e2d7efe-5902-4802-ab5a-cdf4065e8d74`.  Teardown drain time is therefore not
a sufficient fix.

Patch 0063 instead changes receiver error recovery.  FIFO overflow remains
fatal, but packet-level ECC, CRC, header, and word-count events mark the
in-flight frame damaged.  The driver keeps that buffer private and overwrites
it with the next complete frame instead of calling `vb2_queue_error()` and
tearing down the stream.  On boot `74f66f55-f813-4524-a201-83cd6ff92ab5`, the
same rapid matrix completed 12/12 full 5,529,600-byte captures while recovering
through four logged CRC/word-count events.  A subsequent 50-cycle soak
completed 50/50 while recovering through 18 additional logged CSI events.
A continuous three-frame stream then returned sequences 0, 1, and 2 and
16,588,800 bytes.  No incomplete frame reached userspace; systemd remained
`running`, `Unevictable` and swap remained zero, and memory returned after
teardown.

## Old-root leak: proof

The production static census supplied with the investigation found 22,577
pages (88.2 MiB), all `unevictable + uptodate + dirty`, with no anon/slab/
buddy/mmap/swapcache/swapbacked pages.  The census and notes are retained
outside the repo under
`/mnt/Home/src/nixos-nanokvm-artifacts/ram-audit-20260830/`.

The pre-fix eth-NFS initrd was
`/nix/store/k641prxgcdvdh14ym5hqdbchjsv702m0-initrd-linux-riscv64-unknown-linux-gnu-7.2-rc5/initrd`:
22,400,556 compressed bytes and approximately 74 MiB extracted cpio.  Its
generated `initrd-fstab` contains `tmpfs / tmpfs x-initrd.mount,mode=0755`.
`/run/initramfs` disappearing therefore does not establish that the old
ramfs superblock was emptied.

The exact systemd 261 implementation is available from
`nix eval --raw nixpkgs#systemd.src`, in `src/shared/switch-root.c`:

* lines 42-89 open the old root directory and classify it with
  `fd_is_temporary_fs()`;
* lines 152-162 successfully run `pivot_root(".", ".")` and then only
  `umount2(".", MNT_DETACH)`;
* lines 164-200 use `rm_rf_children()` only in the MS_MOVE fallback;
* lines 201-205 explicitly state the (false for ramfs) assumption that
  pivot plus umount detached the superblock sufficiently.

The helper itself is fd-based (`src/shared/rm-rf.c:282-294`) and explicitly
stops at child mount points (`src/shared/rm-rf.c:214-224`), so reusing it after
the successful pivot does not recursively erase the transferred API mounts.

The manager does request the cleanup flag: `src/core/main.c:2178-2182`
passes `SWITCH_ROOT_DESTROY_OLD_ROOT` for `MANAGER_SWITCH_ROOT`, and
`nixos-init` calls `systemctl --no-block switch-root /sysroot` in
`src/switch_root.rs:10-15`.  The missing cleanup is therefore in the
successful-pivot implementation, not in the NixOS handoff request.

The private mount-namespace reproducer used a 16 MiB ramfs payload and the
same pivot/umount sequence.  Evidence is
`/mnt/Home/src/nixos-nanokvm-artifacts/sg2002-stability-pivot-proof-20260830/pivot-proof-2.txt`:

```text
before payload: Unevictable 169920 kB
after payload:  Unevictable 186048 kB
pivot_rc=0
after pivot+umount: old-root fd still stats a 16777216-byte payload
after unlink:    Unevictable 169920 kB
```

The payload remained reachable through the old-root directory FD after the
mount was hidden and detached; unlinking it returned exactly 16,128 kB.
This proves the leak is the successful-pivot path, not a misleading
`MemAvailable` reading and not a stage-2 process RSS issue.

## Candidate fix

Commit `fa1e99b` adds
`patches/systemd/0001-switch-root-clean-detached-initrd-ramfs.patch`.  It
calls the existing fd-based `rm_rf_children()` cleanup after successful
pivot/umount whenever `istmp > 0`, with mount-boundary protection inherited
from the fallback path.  `platform/sg2002-board-support.nix:32-42` selects
the patched systemd package for the CV181x platform; the patch is generic
systemd behavior while selection is limited to SG2002 targets.  The old PCIe
comment claiming that `preserveInitrd` itself controlled ramfs lifetime was
reworded in `boards/nanokvm-pcie.nix:34-39` and
`profiles/sd-image-mainline.nix:34-36`.

Commit `e33a697` repairs the live-root handoff around that platform package:
`modules/usb-nfs-live.nix:36-40,286-290` and
`modules/usb-nbd-live.nix:21-24,113-116,245-246,464-468` use
`config.systemd.package` for initrd helper `systemctl`/`udevadm` paths.
Without this, PID 1 used the patched package while `initrd-cleanup.service`
looked for an unpatched store path that was absent from the initrd, producing
the `203/EXEC` failure above.  The fix is generic to both NFS and NBD live
profiles; it does not change the production PCIe service policy.

The candidate runner
`/nix/store/ly6vrn3abp1v4dyj767xcsk8wnvbflk5-usb-boot` built successfully and
was copied to `strix-1`.  Its initrd is
`/nix/store/sg7bkfazp85kpncd0k51iy646k3fdbyq-initrd-linux-riscv64-unknown-linux-gnu-7.2-rc5/initrd`:
22,454,316 compressed bytes and 67,783,168 decompressed cpio bytes, versus
22,400,556 and 67,785,216 for the pre-fix image.  The candidate systemd
package derivation records the patch as
`/nix/store/qi6838vj90ckyica591n40mmx03a9h69-systemd-riscv64-unknown-linux-gnu-261.drv`.

### PicoClaw fallback

Because `strix-4` itself flapped, the authorised fallback was prepared on
`fuckup`.  The PicoClaw has no usable RJ45 carrier (`enp11s0` and
`enp8s0f0np0` both reported `NO-CARRIER`), so it can only validate USB
recovery/NFS, not Ethernet/NFS or GC4653 multimedia.  The corrected generic
USB/NFS runner `04y1m96xf7xib8v2dk9jabixd217z5jz-usb-boot` was copied and
started, and the WiFi-rooted runner `a75kw34islmb6fipmgz8bxq8icrsc27y-usb-boot`
was also built and copied to avoid making the live root depend on USB NCM.

Neither runner reached BootROM: the board was already cycling its old
composite gadget.  Host `fuckup` recorded:

    cdc_ncm ... usb0: NETDEV WATCHDOG ... timed out 5385 ms
    usb 3-1: USB disconnect, device number 28
    cdc_ncm ... usb0: NETDEV WATCHDOG ... timed out 5706 ms
    usb 3-1: USB disconnect, device number 29

The new runner emitted only
`[usb-boot] verified local NFSv4 exports for 10.55.0.0/24 (/export/nix-store)`
and remained in its ROM wait loop (PID `1964743`); no `3346:1000`,
`18d1:d00d`, or new gadget appeared.  This is a pre-switch-root USB/NCM
transport failure and counts as zero boots.  Full evidence is at
`/mnt/Home/src/nixos-nanokvm-artifacts/sg2002-fuckup-usb-failure-20260830/evidence.txt`.

## Hardware limitation and remaining tests

After the original baseline's blocked ACM writer, USB removal, xHCI
controller unbind/rebind, and host port power-cycle attempts produced
repeated descriptor timeouts (`-110`, then address `-62`).  Physical
restoration was nevertheless followed by five successful corrected target
cycles and the queue-budget A/B above.  Those prove the old-root cleanup,
zero-swap memory recovery, and Ethernet live root; they do not prove five
separate cold BootROM downloads because the campaign used software reboots
after the initial handoff.

The rapid-restart failure is now recovered in the capture driver and has a
62-cycle plus continuous-stream hardware result.  The sensor still emits
intermittent startup CRC/ECC/word-count events, so eliminating their electrical
or sensor-internal cause remains a quality improvement rather than a stream
reliability blocker.  A cold BootROM/FIP/FIT cycle, deliberate USB-recovery
test, and the 32 MiB tmpfs pressure case remain useful transport checks.  The
duplicate initrd/stage-2 DHCP ownership noted above should be cleaned up
separately; it did not retain old-root RAM or divert the NFS data path to USB.
